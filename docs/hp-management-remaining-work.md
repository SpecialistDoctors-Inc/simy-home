# HP更新サービスの残タスクと利用開始条件

2026年11月3日時点。AWSの常時稼働サービスは、サンプルの既存お知らせ本文について、受付から確認用ページ・通知メール受信まで検証済みです。**利用者だけで安心して使える運用にするには、途中で止まった依頼の検知・連絡・復旧が残っています。** 当面の案内は運用担当が同席する試用とします。

今回準備したのは実施計画と案内文です。以下の追加実装、障害試験、権限変更、通知送信を実施済みとは扱いません。担当欄は役割の割当案であり、tshiwakuさんへの開発作業の割当ではありません。

## 利用者だけで使い始める前に必要なタスク

P0は通常運用の前提です。まずR01〜R03とR05を整え、R04でまとめて検証します。

| ID | 優先 | タスクと現状 | 担当案 | 完了条件 |
| --- | --- | --- | --- | --- |
| R01 | P0 | 依頼ごとの停滞・未解決エラーの監視。現在は直近のサービス動作が中心で、保留依頼が残ったまま監視が正常に戻る可能性がある | 開発・運用 | 工程の開始時刻・最終進捗・次の対応者を保存。工程の期限超過と未解決の保留を検知し、受付の再開だけでは解決扱いにしない。人の公開承認待ちは障害と区別 |
| R02 | P0 | 運用担当への障害通知と対応追跡。監視の外部通知先は未設定 | 運用 | 宛先・対応時間・代理担当を決め、Google接続停止中も届く別経路を接続。障害通知の実受信、担当者の受付、復旧通知まで確認。重複通知を抑え、依頼本文や認証情報を載せない |
| R03 | P0 | 上限付き再試行と明示的な復旧操作。現在、作成・レビュー中断や結果不明の処理は運用判断待ちになる | 開発・運用 | 安全な読取りと未着手が証明できる操作だけ再試行。回数・待機時間・総時間・費用に上限を設ける。再開前に現行revision・取消・権限・成果物・外部結果を再照合し、完了工程を繰り返さない |
| R04 | P0 | 途中停止を起こした一連の試験 | 開発・独立レビュー担当 | 下表の障害を隔離環境で再現し、検知→通知→復旧→結果照合まで確認。変更・PR・メールの重複0件、未確認の公開0件。対象コードの独立レビューとCIに合格 |
| R05 | P0 | 認証失効時の引継ぎ手順 | 運用 | Google・Codex・GitHubそれぞれの失効を検知し、必要な本人操作を案内できる。失効を模した試験で依頼を保持し、再接続後に同一対象を照合して復旧。稼働中の認証を試験のために失効させない |

R01の根拠は[現在の死活確認](../infra/hp-agent/health.py)と[依頼の進行処理](../examples/hp-management/runner/agent.py)です。`needs_input`の依頼は通常の進行対象から外れるため、後続の`idle`だけを正常判定に使うと未解決依頼を追い続けられません。R03では、確認待ちの依頼が他の独立した依頼を妨げないことと、外部結果が不明な同一サイトでは必要な排他を維持することを両立させます。

### 障害試験で確認すること

| 停止させる箇所 | 期待する結果 |
| --- | --- |
| Sheetの読取り中の通信断・一時的な制限 | 間隔を空けて上限付きで再試行。復旧後に同じ依頼を1回だけ取り込む |
| Codex作業中・テスト中・独立レビュー中 | 作業の所有者と保存済み成果物を確認して停止理由を記録。担当者に届き、安全な工程から復旧。既存プロセスと二重実行しない |
| PR作成直後・統合直後に応答が途切れる | GitHubの実結果と入力を照合。既に成功した操作を再発行しない |
| CIや配備が失敗・長時間進まない | 完了通知を出さず、期限超過を担当者へ通知。修正後は新しい成果物として検証し、古い承認を流用しない |
| 配備成功後、Sheet記録前に停止 | 実配信ファイルを照合し、足りない結果記録から再開。サイトを再配備しない |
| メール送信直後、送信結果の保存前に停止 | 送信済み記録を照合して履歴を補う。不明のまま再送しない |
| 途中で取消・新revisionが到着 | 古い依頼の実装・配備・送信を新たに進めない。既に実行中の送信との排他を尊重し、取り消せた範囲を記録 |
| 受付は動いているが一部の依頼だけ保留 | 保留依頼の警告を維持。正常な依頼や公開承認待ちと混同しない |

工程の期限、再試行回数、通知の再案内間隔、対応時間は設定値として決めます。まだ実測・合意していない「何分で必ず完了」などの約束を案内に含めません。

これらは計画の準備までです。今回の案内準備に、サーバー再起動、認証変更、障害通知の接続、本番公開の実行は含めません。定期バックアップの読戻し結果などで状態が変わった場合は、日時と証拠を添えて本書を更新します。

## 作業を閉じる条件

各タスクには実際の担当者、状態、次の対応、証拠、完了日時を記録します。「処理が止まった」「メールを送った」だけで完了にしません。正常終了、理由付きの取消、担当者が引き受けた要対応を区別し、要対応は解決または利用者との中止合意まで追跡します。

既存の受入receiptは原本として保持します。追加試験には別の記録を作り、対象revision・成果物・環境・外部送信回数を記載します。プロセス停止は、その作業で自ら起動してPID・PPID・command・startを記録した正のPIDに限り、直前に同一性を再確認します。名前・pattern・group・treeや共有サービスを清掃目的で停止しません。
