## Beneficiaries and end-to-end promise

A first-time Japanese or English visitor arrives from search or the home page with a real sales or engineering job. On the website, they should find the relevant route, see what information SIMY needs, inspect a representative output and its human review boundary, understand prerequisites, and reach a usable start action. If a destination is unavailable, they should retain their task context and know a safe alternative. A real product task result is a separate, stronger promise and requires a synthetic task observed in SIMY; sample text cannot stand in for it. All claims about demand, features and availability must retain source and date. No ranking, conversion or first-task success is inferred from a page count.

## Neutral first-read test script

Recruit a reader who did not author the pages. Do not show the expected answers or describe the UI first. Say: “You sell a service and must prepare a follow-up after a meeting. Find where SIMY could help. What would you give it, what would you get, what would you review yourself, and what would you do next?” Then: “You review a proposed AI code change. Find the path that explains how to request and verify it. What does an SQM pass establish?” Give the rendered page and a normal browser only. Record first click, navigation changes, answers verbatim, hesitations, wrong turns, and whether recovery succeeds. Passing UX-01/02/03/04 requires independent correct answers defined above, not a tester being able to find a link after prompting. If no fresh human reader is available, retain comprehension rows pending; an AI review of copy can find defects but is not a user study.

## Shared-view and release boundaries

Screen inventory: existing home, hubs, occupation pages, guide pages and downloads; route list above. Transitions: UX-01→02→03/04→05→07, with UX-06 crosscutting. Wireframes: source HTML is As-Is; To-Be changes must link a UX ID and show desktop/mobile states. Functional requirements: UX/SEO/REL table here. State machines: static navigation; external product setup/task state remains unknown until exercised. Permissions: anonymous site reader; product actions require actual account and user authority; no auto-send/publish. User workflows: the complete path above. Data dictionary/ER: no new website persistence or DB; old analytics remains separate and consent-aware. Sequences/API: static CloudFront/S3 delivery and browser navigation; downstream product/installer endpoints must be verified before any claim. Infrastructure: GitHub main deploy to S3/CloudFront, literal slash keys for `/for/`, no IAM/function change in this scope. Any security/config mutation raises floor to level 5 and needs user direction.

Release ledger fields (pending until candidate exists): CLI run ID; clean worktree path; base SHA; candidate SHA and diff; current design review; final independent review; SQM min/full signed proof and zero/nonzero rule coverage; PR URL/head/base/status; CI exact check; deploy workflow ID; live URL/content comparison; browser journey screenshots; rollback trigger and owner. The site owner owns that observation; no automation created without request.
