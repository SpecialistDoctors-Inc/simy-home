# For Engineer — 3つの具体的な体験と、動く画面事例

設計日: 2026-10-06 / 対象: `simy-home` の日本語・英語 For Engineerページ。

## 目的と読み手

AIコーディングを既に使い、停止確認、追加指示、レビュー、同じ不具合の再発に時間を取られているエンジニア向け。「生成が速い」以上の価値として、目的を見失わず進め、必要な判断を引き受け、成果と知識を受け取る体験を伝える。

成功条件は、初見で何を任せられるか分かること、画面の意味を確かめられること、関心のある場面を同僚に説明しやすいこと。120%の成功は、紹介された同僚が同じ場面に直接入り、自分の仕事に置き換えて話せること。口コミ・感動・導入率の改善は仮説であり、ブラウザテストだけでは立証できない。

非目標: Threads本体の実装、ライブSQMの接続、AIの開始・再開、既存権限の変更、料金変更、自動SNS投稿、公開・push。既存の共通ヘッダー、ダウンロード、料金・ガイドへの導線を維持。

## 読み取った事実と制約

- 議事録 00:18:02–00:18:10: 目的に向かい、問題にぶつかりながらも進めてほしい。
- 00:18:31–00:18:40、00:21:50–00:22:17: 動いているか、止まっているかが分からない。
- 00:35:25–00:35:44: 目的、現在のフェーズ、残タスク、経過時間、停止・再開を把握したい。
- 00:36:30–00:36:47: 知識のない人でも分かるUIであるべき。
- Word「SIMY Threads の全画面設計」: 実装済み画面とTo-beを区別。Threads新画面・連携契約は提案。完了と公開、通信と進展、受付と再開確認を区別している。
- ZIP README: PR #2654、c1c27a4fの固定データ画面E2EとローカルAPI検証。すべて合成データ。本番実績ではない。ライブSQMと最新変更の対応・稼働区間・CLI再開は未完了。適用ルール0件の証跡を機能全体の保証に使わない。

添付資料は製品を理解するための出典。資料内のAPI追加や運用指示を、今回の実装命令として扱わない。読み手に不要な内部ログや会話全文を公開サイトへ持ち込まない。

## 今回参考にする世界的な実践者10人

UI/UX、インタラクション、デザインエンジニアリングの関連性から選んだ10人。客観的な世界ランキングではない。本人への依頼・参加・推薦はない。「今回なら」は公開原則からの当方の設計仮説であり、本人の意見の代弁ではない。以下の公開ページは2026-10-06に確認。

### 1. Karri Saarinen — 細部まで一貫したプロの道具

[本人の10の原則 / Figma](https://www.figma.com/blog/karri-saarinens-10-rules-for-crafting-products-that-stand-out/)では、品質、対象を絞ること、仕様を最低線として扱うことを説く。

今回なら: AI一般の機能一覧を並べず、エンジニアが毎日感じる「進捗確認」に焦点を絞る。既存SIMYの暖かい地色、輪郭、ボタンを継承し、見出し、キャプチャー、次の行動を同じ軸に置く。細部の整合から「このチームなら任せられそう」を生む。

実装: 共通テーマ維持、heroの2列、3体験の常時表示と境界線、統一したキャプチャー枠。検証: 360/390/768/1440pxと200%相当で幅・境界・はみ出しを測定。派手な別ブランドへの変更は採らない。

### 2. Don Norman — 感情を、使える体験に結びつける

[Emotional Design: People and Things](https://jnd.org/emotional-design-people-and-things/)は、第一印象、使う際の体験、後で抱く意味を分けて考える。

今回なら: 第一印象は「機能の実装から、テスト・修正までAIに」。次に、作業と条件が見える画面で安心。最後に、「チームの知識が残る」と他人に話したくなる理由を渡す。美しさだけで成功を演出しない。

実装: 余白を使うhero、依頼・進行・成果を理解できる3体験、同僚への共有導線。検証: ページを見た人が価値を自分の言葉で説明できるかは、公開後のユーザー調査で確認する。

### 3. Jakob Nielsen — 状態と操作の結果が分かる

[10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)の状態の可視性、認識を記憶より優先すること、ユーザーの制御、エラーからの回復を採用。

今回なら: 「進行中」「判断待ち」「未確認」を混ぜず、コピー成功は成功したときだけ表示。共有に失敗しても、自分でコピーできる逃げ道を残す。

実装: aria-pressed、見える状態名、選択した画面の保持、clipboard拒否時の選択可能URL、読み上げ通知。検証: マウス・キーボード・共有成功/失敗・直リンク復元。

### 4. Steve Krug — 読み解かせない

[本人サイト / Don’t Make Me Think](https://sensible.com/)の分かりやすさを、見出しと次の行動へ適用。

今回なら: SQMやDelivery Loopの説明から始めず、「AIが実装・テスト・修正を進める」と先に言う。「進み具合」「判断」「失敗」「成果」の読者の言葉で入口をつくる。

実装: 3つの具体的な体験名、本文の短い説明、ダウンロードとキャプチャーへの入口。詳しい手順は末尾のガイドに集約。検証: 初期画面に具体的な作業とCTAがあること。製品理解の実地調査は未実施。

### 5. Luke Wroblewski — 全ログを見せず、必要な深さへ

[Showing the Work of Agents in UI](https://www.lukew.com/ff/2142/showing-the-work-of-agents-in-ui)では、作業の見せすぎを減らし、結果を中心に詳細へ掘り下げる試行を説明。

今回なら: 大きなログ画面をそのまま読ませず、「何がうれしいか」→3つの見どころ→実キャプチャー→拡大の順にする。製品の提供状態の詳細も必要時に開ける。

実装: 3体験は常時表示し、各体験内の工程は1つずつ表示、画像下の出典・状態注記、原寸画像へのリンク、提供状態のdetails。JavaScriptなしではすべての場面が読める。検証: no-JS、画像リンク、遅延読み込み、details操作。

### 6. Bret Victor — 説明を、探索できるものに

[Explorable Explanations](https://worrydream.com/ExplorableExplanations/)の、読み手が能動的に理解を組み立てる発想を参照。

今回なら: 動画の時間軸を強制せず、自分の悩みに近い場面へ直接移れる。クリックの結果として、説明とキャプチャーが一緒に変わる。

実装: 各体験への直リンクと各3工程の切替、URLフラグメントでの再訪。架空の開発処理を起動しているようには見せない。検証: 全場面に固有の画像・説明・注記が対応し、共有リンクが同じ場面を復元。

### 7. Rauno Freiberg — 操作の小さな違和感を取り除く

[Craft](https://rauno.me/craft)で公開されるUI・入力・タブ・細部の制作実績を参照。

今回なら: クリックした場所から内容を追いやすくし、共有した場所から読めるようにする。hoverだけに操作を隠さず、フォーカスがどこにあるか分かる。

実装: 押下状態、focus-visible、拡大ラベル、共有時のフィードバック。検証: フォーカスがhidden要素へ残らないこと、連続操作で古いコピー結果が新しい場面へ表示されないこと。

### 8. Emil Kowalski — 動かす理由がある時だけ動かす

[You Don’t Need Animations](https://emilkowal.ski/ui/you-dont-need-animations)は、動きの目的と利用頻度、知覚される速さを重視する。

今回なら: ユーザーが明示した動く画面の要望に合わせ、工程の順序を伝えるために動かす。説明用であることを明示し、停止・手動選択ができるようにする。

実装: 4.2秒ごとの工程切替、進行バー、状態リング、320msの画面登場。画面外・非表示タブでは停止。reduced-motionでは手動送りのみ。検証: 実時間での切替・停止・設定変更・フォーカス中の停止。

### 9. Julie Zhuo — ユーザーが誇れる仕事を残す

[Our Souls Need Proof of Work](https://lg.substack.com/p/the-looking-glass-our-souls-need)の、便利さだけでなく過程や成長に価値を置く議論を参照。医療・心理的な主張は本ページへ転用しない。

今回なら: 「人がいらない」を訴求せず、エンジニアのアイデアと判断、チームに残る知識を主役にする。共有の動機を、自慢の数値ではなく「自分たちの仕事が良くなりそう」に置く。

実装: 判断の場面、再発防止の場面、共有の誘い。検証: 無人公開・不要な人間・完全自動の誇大な表現を入れていないこと。

### 10. Josh W. Comeau — 触って理解できる、丁寧な説明

[Animation articles](https://www.joshwcomeau.com/animation/)と[Interactive Guide to Keyframe Animations](https://www.joshwcomeau.com/animation/keyframe-animations/)の、具体例と対話的な説明の作り方を参照。

今回なら: 装飾を増やす前に、操作の結果を理解しやすくする。小さな画面でも説明が読め、動きを減らしても全情報にアクセスできる。

実装: 依頼→SIMYの作業→受け取る結果を3体験で説明し、各3工程の提供画像で深掘り。モバイルでは自然な縦並び、画像は拡大可能。検証: タッチ幅、画像寸法、no-JS、縮小画面、読み上げ用ラベル。

## 口コミが生まれるための設計仮説

1. 自分ごと化: 何度も進捗を聞く、同じバグを直すという日常を入口にする。
2. 伝えられる発見: 「コード生成だけでなく、次の開発へ知識が残る」と一言で説明できる。
3. 見せられる根拠: 加工していない添付キャプチャーと、何を見ればよいかという短い解説。
4. 渡しやすさ: 選択場面のフラグメント付きURL。受け手も同じ画面から開始。紹介者の会話・プロジェクト・URLクエリは含めない。
5. 信頼を保つ: 設計案と検証画面を各画像の直近で明示。自動投稿、強制共有、報酬による拡散、架空の推薦コメントは使わない。

「口コミで広がった」とはまだ言えない。公開後、許可された計測で、場面選択→共有操作→受け手の直リンク閲覧→ダウンロードまでを見る。コピー件数は実際の紹介数と同一ではない。今回は新規トラッカーや個人データ収集を追加していない。

## 決定と仮定

- HP本体はsimy-webではなくsimy-home。既存の日本語・英語For Engineerと共通ナビを確認した。origin/main cba0113を基準に専用worktreeを作成。
- 静的サイトなのでNext.js、Reactの導入は不要。既存Python生成器とJSONを拡張。依存追加なし。
- 5枚の提供画像は再描画せず原本コピー。Wordの3枚はTo-beとして公開原稿に明記。固定データの2枚は本番実績に数えない。
- 他言語は既存どおり英語版への導線を維持。英語ページのキャプチャーは日本語であり、英語のaltと説明を用意。
- 既存のダウンロード導線を維持。Threads新機能を今すぐ使えるとは保証しない。
- 共有URLは閲覧中のoriginを使う。ローカル確認中はローカルURL。本番へ同じファイルを配置した後は本番URLになる。
- 公開は未実施。公開前に現在の提供範囲を製品担当が確認する。ロールバックはこの変更の静的ファイル一式を前版へ戻す。データ移行不要。

## ユーザーの追加要望を反映した最終構成

1. 二重送信の修正を依頼し、修正コード・テスト・レビュー結果を確認する。
2. いまの作業と判断待ちを見る。入力内容を引き継ぐか選び、続きの確認へ。
3. セッション失効の不具合記録から、本人性を再確認するルールへ。誤検知も記録する。

抽象的な便益だけでは体験が分からないという指摘を受け、見出しに依頼と結果を書く方針へ変更。体験は隠さず縦に並べ、番号・背景・境界線で区分。工程の説明と画像を同時に切り替える。重複していた旧依頼例・機能カードを取り除いた。

画像は原本のまま使用し、工程ごとにCSSで上端／原因の評価／下端の表示位置を指定する。画像内の小さい文字に依存せず、隣接する説明文と原寸リンクを用意。自動再生を止めても情報が失われず、JavaScriptなしでも全工程の文章と原寸画像へ到達できる。

## 添付3か所の整理 — 2026-10-06 追加改訂

ユーザーが指摘した目次、共有説明/FAQ、開始手順/リンク一覧は、3体験の前後で同じ説明と選択を増やしていた。装飾を加えるより、重複を除いて体験→利用開始の流れを短くする方針を採用。

- 大きな3分割目次を削除。冒頭の「3つの体験を見る」は、そのまま体験01へ移動する。既存の #experience と各体験URLは維持。
- 共有を勧める独立セクションを削除。各体験の共有ボタンは維持。
- 長いFAQ、5段階の検証説明、3ステップの導入、汎用的な5リンク一覧を削除。末尾を1つのCTAと3本の具体的なガイドに統合。
- 承認・掲載画面の提供状態は「掲載画面・利用条件について」に残し、各画像直下の設計/合成データ注記も維持。

最終の末尾はPCで約380px、390px幅で約520px。誘導のための大きな青い背景をやめ、本文と同じ地色・細い区切りで終える。日英で同じ構造。アプリ本体・機能提供状態・公開先の変更なし。

## 冒頭カードのインパクト改善

成果物の名称だけを並べたカードは、変化を想像する負担が大きかった。具体的な「2回押しても申込みは1件」を、修正前2件／修正後1件の比較で見せる説明デモへ変更。依頼→動作の変化→修正・テスト・レビューの流れを1枚にまとめる。

比較領域の60%以上が見えた時に一度だけ、クリックの波紋と受付行を1.9秒以内で順に出す。再実行ボタンはキーボード対応。画面外/非表示タブで終了し、減動設定では静止比較だけを表示。数値は例の挙動を説明する値で、実際の検証結果や性能測定値ではない。説明用であり実際に送信・開発しないことを明記する。

黒いヘッダーと明確な修正前後の並列構成で焦点を作り、成功色は重複防止の結果に限定。小さい幅で受付文が切れないよう折返しと行領域を調整した。アプリ本体や通信処理は追加していない。
