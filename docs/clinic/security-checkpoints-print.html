医院側の設定と提供会社側の仕様・回答を分けて確認します。外部サービス内部の検査には、提供会社の許可が必要です。

連携先／渡る情報の例確認する問題・根拠確認を担う人停止・障害・再開
Web予約・Web問診氏名・連絡先・予約日時・症状などURLやアクセス解析に氏名・症状が混ざらないか。予約番号だけで他の患者の情報を見られないか。確認資料：テスト患者の送受信記録、閲覧権限、保存期間、データ出力・削除方法。医院が契約・利用者・送信項目を確認。制作会社が接続設定を確認。提供会社がサービス内部を確認。障害時は電話受付へ切り替え。復旧後に予約の抜け・重複を照合。
オンライン診療・電子カルテ連携患者識別子・診療関連情報・添付ファイルなど別の患者へのひも付け、過剰な取得権限、失敗時の部分更新を防げるか。確認資料：送信項目一覧、患者照合の仕様、テストデータによる取込・拒否・再送の記録。医院と各提供会社が対象範囲を合意。制作会社が医院側の連携部分を確認。連携停止と診療継続の手順、未反映データの照合。内部の診断には提供会社の許可が必要。
決済・会計連携決済用の識別情報・金額・支払状態カード情報を医院HPやログに不要に保存していないか。偽の支払完了通知や再送で二重請求にならないか。確認資料：テスト環境で通知の送信元確認、重複防止、金額照合、返金・取消権限を確認。医院が契約・返金権限、制作会社が連携、決済会社が内部処理を確認。障害時の未決済一覧と手動照合。再送時に同じ請求を重ねない。
LINE・メール・SMS宛先・予約案内・認証コード・問い合わせ通知通知本文やロック画面に症状を載せすぎていないか。送信キー流出時に大量送信を止められるか。確認資料：テスト宛先への通知内容、送信専用権限、コードの期限・試行制限、誤送信時の連絡先。医院が宛先と本文、制作会社が送信設定、提供会社が配信基盤を確認。送信停止・キー失効・交換、送信量上限、失敗時の再送と重複通知の抑制。

実際の連携先・送信項目・保存先・権限・接続キーの失効方法を一覧化します。報告書に患者情報や秘密の接続キーそのものは載せません。
