## 利用者を追加するとき

1. 対象のGitHubリポジトリ、GitHub Appのインストール、検証ワークフロー、確認用・公開用のS3 / CloudFrontを確認します。
2. Driveの原本・変更受渡しフォルダー、記録用Sheet、通知先を対象サイトに紐付けます。署名付きの直接受渡しを使える設定も確認します。
3. Googleログインに使う本人のアカウントを確認し、サイトの招待と `read` / `edit` / `publish` の権限を設定します。利用者のGitHubアカウントは不要です。
4. 利用者本人がGoogleログイン・許可を完了した後、`hp_profile` と `hp_list_sites` で本人・サイト・権限を読戻します。
5. 利用者の実機で、ZIP導入、起動、ローカル編集、確認用への反映、確認画面まで検証します。公開テストは対象の確認済み成果物への承認を得て行います。

新規サイトの検証・登録は `examples/hp-management/control/provision_site.py` が入口です。最初に `--apply` を付けずに入力を検証します。新規登録専用なので、既存サイトや既存利用者の更新には使いません。招待は7日で期限切れになります。既存サイトへのメンバー追加は、現在の本人情報・権限を読み、条件付き更新で行います。

現在のHPログインは `openid email` を使うため、外部テストモードでも基本認証スコープ向けの例外が適用されます。基本認証以外のスコープを追加する場合は、Google側のテストユーザー設定を確認します。[Googleの対象ユーザー設定](https://support.google.com/cloud/answer/15549945?hl=en)

認証情報、本人確認書類、審査用パスワードは配布ZIPや手順書に含めません。

## 版番号と変更概要

番号はサイトごとの検証済み成果物に付きます。`content-version:<site>:<artifact>` の記録と、サイトの `last_content_version` を、確認用反映の完了記録と同じトランザクションで確定します。再試行や本番公開で別の番号を作りません。

サンプルクリニックは、既存の確認用・公開中の同一成果物をv1として導入しました。過去全履歴を通算した番号ではありません。番号未設定の古い成果物は「—」と表示します。

概要は公開中のソースと、確認済みの候補ソースの差分から作成し、公開確認時の対象に固定します。文章は変更前後を最大120文字、概要は最大5件と残り件数で表示します。比較負荷を抑えるため、ファイルサイズ・テキストブロック数に上限があります。画像・CSSなどは変更種別の説明になります。

基準版が一致しない、または古い原本が比較できない場合、概要は取得できない旨を表示します。状態や概要だけで公開権限を与えず、本人の確定とサーバー側の成果物照合を保ちます。

サンプルの既存公開履歴には、正確なGitHubツリー・ファイルを照合して概要を補いました。紹介文の変更前後と、見出し「毎日」の文字サイズ・色の変更です。

## プラグイン更新

- 作業領域の `site/` と `.hp/`、未完了の保存・公開処理を確認します。実行中の処理は元のIDで照合します。
- 配布ZIPを固定の保存場所へ展開します。登録済みマーケットプレイスの参照先と、実際のプラグイン版を確認します。
- 関連するプラグインを更新し、ホストが今回の版を読み込んだか確認します。読み込まれず再読込みでも解消できない場合は、作業を保存してアプリを再起動します。Google接続を再利用できることと、起動したローカル画面の版を確認します。
- 作業領域は引き継ぎます。別セッションが所有するプロセスのロックを削除して強制起動しないでください。

ローカルプラグインの登録と更新は、現在のホストが対応する方式に従います。[公式手順](https://developers.openai.com/plugins/build/plugins#install-a-local-plugin-manually)

## 中断・障害時の扱い

| 状態 | 運用側の確認 |
| --- | --- |
| ローカル編集の中断 | `.hp/chat` の元の依頼・候補とファイルを照合し、再開可能な処理を続行 |
| 保存の応答が不明 | 元の操作IDと変更パッケージを保持し、受領結果を読戻す |
| 確認用反映が不明 | 元の操作・検証・配信結果を照合。新しい依頼の重複作成を避ける |
| 公開ボタンの後で中断 | 元の確認ID・公開操作を読戻す。未完了の確認を別操作で迂回しない |
| 通知だけが未完了 | 公開と通知の状態をそれぞれ確認。通知の再試行でサイトを再公開しない |
| needs_attention | 停止理由と外部副作用を照合してから、同じ操作の再開可否を判断 |

プロセス停止は、当該作業で起動時にPID・親PID・開始時刻・コマンドを記録した対象だけを扱い、直前に同一性を再確認します。共有ブラウザーや他作業のプロセスをまとめて終了しないでください。

## この配布セットを再作成する

`HP_PLUGIN_ROOT` は `simy-hp-skills` の作業ツリー、`HP_RELEASE_NATIVE` はまだ存在しない出力先に設定します。以下は運用担当が `simy-home` のルートから実行する手順です。

```sh
cp docs/hp-single-plugin-customer-guide.md "$HP_PLUGIN_ROOT/plugins/hp-local-editor/skills/hp-local-editor/references/customer-guide.md"
"$HP_PLUGIN_ROOT/output/build-env/bin/python" "$HP_PLUGIN_ROOT/tools/build_desktop_plugin.py" --output "$HP_RELEASE_NATIVE"
uv run --with reportlab python docs/build_hp_plugin_guide.py --output output/hp-plugin-0.3.12-20261108
python3 docs/package_hp_plugin_release.py --native-build "$HP_RELEASE_NATIVE" --output output/hp-plugin-0.3.12-20261108 --date 2026-11-08
```

ビルド環境の初回準備は `simy-hp-skills/tools/README.md` に従います。組立スクリプトは、ネイティブZIPの検証後に配布名へコピーし、利用者向けの依頼文と配布セットZIPを生成し、ビルド記録は運用側に保存します。PDFは生成後に各ページをレンダリングして確認します。展開・インストール後は `bin/hp` の実行権限と `doctor` の結果も確認してください。
