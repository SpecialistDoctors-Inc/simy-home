## 顧客導入時の確認

1. 対応OSとPython 3、Codexのホスト版を確認し、検証した固定40桁コミットとZIPのSHA256を案内する。可変ブランチや旧受付スキルを代用しない。顧客にGit・GitHub・SIMYアカウントを要求しない。
2. 顧客が利用するGoogle本人と対象サイト権限を、運用側の招待または登録済みの対応付けで準備する。Googleの検証済み本人から権限を解決し、Sheetの記載やメールドメインだけを権限根拠にしない。
3. HPプラグインとDriveを別に接続し、実プロフィールで同じ本人と確認する。Driveのpermission IDをGoogle OIDC subjectと比較しない。接続不一致では転送を止め、権限を勝手に広げない。
4. `hp_profile`、`hp_list_sites`で本人・対象を確認する。認証済みの作業領域作成結果にある取得元・アップロード先だけを使う。フォルダー名検索や顧客が貼った別IDへ置き換えない。
5. 固定プラグインに同梱されたヘルパーで原本と受領結果を照合する。導入・接続確認だけの依頼で、編集・保存・公開を始めない。

個人のChatGPT/Codexへの登録や所有者操作が必要な箇所は、必要な本人の許可・画面操作を得る。ネイティブ操作のブロックを別経路で回避しない。現在のアカウントでの試験と、後日行うtshiwaku本人の導入・受入れを混同しない。

**Google側の対象範囲も確認する。** 2026年11月5日の実管理画面では、現在のGoogle認証プロジェクトは `Internal` だった。今回の社内アカウントの試験結果を、別組織や個人Gmailの接続成功と扱わない。別組織の利用者を導入する前には、本人確認だけを扱う外部向け接続を準備し、実際の本人で確認する。運用用Drive／Gmailの権限を持つ既存接続の公開範囲を、この案内だけを根拠に変更しない。

利用者が運用担当と別のGoogle本人の場合、サイト専用の原本取得フォルダーと変更提出フォルダーへの共有も必要になる。HP側の権限登録だけでDriveの共有は完了しない。必要な取得・提出の権限だけを設定し、本人のDrive接続から実ファイル取得・提出を確認する。tshiwaku本人のアカウント・共有・接続は後日の対象である。

## 保存と公開の境界

`hp_open_workspace` の完了結果と原本ZIPの全体ハッシュ・サイト・作業領域・基準コミットを照合する。顧客が編集するのは `site/`。`.hp/` は原本、保存待ちパッケージ、受領結果を持つため、作業フォルダーと一緒に保全する。

同梱ヘルパーの `status --diff` で実差分を読み、Codexが短い変更要約を `pack --summary` に渡す。会話全文、メールアドレス、認証情報は保存メモへ入れない。サーバーが信頼済み操作情報を付加する。保存メモは公開権限ではない。

`pack` の操作ID・ZIPバイト列・要約は保存待ちの間は固定する。`hp_save_draft` に同じ操作IDを渡し、完了した `kind: saved` の結果だけを `accept` する。受領はそのパッケージだけに対するもので、作成後の追加編集は次の保存へ残す。下書き保存後も、プレビュー依頼と本人の公開確認は別の操作である。

## 新しいリポジトリのActions有効化

新規の専用サイトリポジトリでは、Actions画面も確認する。今回、RESTのActions権限が `enabled: true`、ワークフローがactiveでも、画面に **Workflows aren't being run on this repository** と **Enable Actions on this repository** が残っていた。

この状態では、AppによるPR作成・更新も、管理者による標準の再オープンもCIを開始しなかった。手動実行だけは成功していた。専用リポジトリの当該ボタンだけを有効化した後、通常のApp保存・synchronizeでPR CIが自動開始し、現在のheadと成果物を照合できた。Appの権限追加や既定ワークフロー権限の変更は不要だった。

したがって、手動の `workflow_dispatch` 成功を自動連携の証拠にしない。チェック専用ワークフローの内容と対象を確認し、必要な有効化の権限を得たうえで、通常イベント・実head・ワークフローID・run・成果物ID・ダウンロードしたバイト列まで確認する。別リポジトリや組織全体の設定へ広げない。

## 残る受入れと切替の順序

1. **確認用環境の切替準備**：明示的に承認された環境だけを対象に、既存の配信設定、原本ファイル一覧、現行内容、復旧手順を記録する。同じバケットへ書く旧dev writerを制御された手順で退役させてから、devの切替権限とプレビューを有効にする。旧 `s3 sync --delete` と `releases/<hash>` の併存は、新成果物を削除し得るため避ける。旧ランタイム全体の廃止とは別の段階である。
2. **実プレビュー**：実顧客候補でGitHubの静的CI、隔離レンダラー、デスクトップ／モバイルの画像確認、確認ページ配信と読戻しを通す。成果物全体のハッシュと実ファイル、削除URLの404、Sheetと通知を確認する。AWS実行許可、健全性エンドポイント、過去の成功runだけで完了にしない。
3. **実Codex公開カード**：現在の確認済み成果物で、本人が実ホストのカードを表示・確認・クリックする。app-onlyツールと非公開メタデータの扱い、本人と最新権限、期限・nonce・成果物・現行プレビューの再検証を確認する。古いカード、変更後のプレビュー、権限取消しなどの拒否も必要。会話の承認文や直接API呼出しを、実カード操作の受入れ証拠に置き換えない。
4. **本番切替**：devとホストの受入れ後、別途の明示的な承認で対象の旧prod writerを退役し、本番権限を有効にする。本人が確認した同じ成果物を再ビルドせず配信し、mainのソース状態と実公開状態を別に記録する。公開URLの全ファイル、バージョン、削除URL、実際の通知・受信を確認する。CloudFrontの伝播は全拠点で同時ではない。
5. **復旧受入れと旧方式の退役**：途中停止、結果不明、通知失敗、取消しと反映の競合を実経路で確認する。新方式・復旧・連絡経路を受け入れてから、承認された旧ランタイムだけを退役する。既存監視、SIMYループ、他のサービスを一括で起動・停止・再設定しない。

第1段階のdev切替と最初の実プレビューは完了している。途中停止のうち、GitHub書込み直後の実プロセス停止とAWSの元メッセージからの復旧も完了した。正常な検証処理の途中取消し、試験ファイルの追加・削除と実URLの404、残る9ファイルの一致、通知先のINBOX到着まで確認済み。ローカルとCodex会話内の確認画面、本番切替と公開まで確認済み。旧専用EC2の停止、停止後のTerraform差分なし確認、未使用キー削除と残存キーによる認証まで確認済み。

## 実プロセス停止の受入れ結果

実GitHubの作業ブランチ更新が成功した直後、親の完了記録を保存する前に、所有確認した試験用プロセス自身を終了コード71で停止した。DynamoDBには未確定の外部処理と元のleaseを残し、実際のlease期限を待って同じSQSマッピングを復元した。手動再キュー、Lambda直接起動、lease書換えは行っていない。

AWSが元の依頼から復旧し、停止前と同じGitコミット1件、Requests1行、draft_savedイベント1件で完了した。手元でも認証済みの完了結果を読み、ヘルパーで受領した。mainとdevは変化していない。この結果は下書き保存の実停止・復旧を示し、本番配信の途中停止まで検証したという意味ではない。

## 二つの公開入口

利用者の希望により、Codexの会話内カードと、ローカル確認画面の右下メニューを用意する。公開の対象・本人・期限・権限・成果物の検証と二重受付防止は同じサービスが扱う。公開用の確認情報を、編集対象のサイトファイルへ埋め込まない。ローカル画面はサイトの表示領域と操作領域を分離する。

公開無効時にも接続を試せるカードを実装・検証し、サーバーへ配備済み。接続テストの確認は監査記録だけを残し、公開依頼を作らない。後から公開を有効にしても、そのカードを本番公開の承認に転用しない。実Codex会話内カードでの確認は別の受入れ項目である。ローカルブラウザーでは、本物のCodex app-serverから接続確認を行い、サービス受付成功直後・手元の完了記録前に所有プロセスを終了コード71で停止した。インストール済みの通常版0.2.0を同じ作業領域で再起動すると、同じ確認番号と結果へ復旧し、ボタンを押し直さずに完了表示になった。私有nonceは記録へ保存しない。これは接続テストの実中断検証で、本番公開の受入れの代わりではない。

公開確認の応答を失った場合は、元の `approval_id` で `hp_get_confirmation` を読み、受付済みの同じ公開操作または接続テストの結果を確認する。`prepared` という読戻しだけでは未実行を確定できないため、再送や新規公開を始めない。確認期限と記録保管は分け、確認記録は操作記録と同様に保全する。未受付の確認をやり直す場合は `hp_cancel_confirmation` が取消しと受付を原子的に競合させる。既に別画面で同じ公開が受け付けられていれば、その操作を返す。取消しを公開のロールバックと扱わない。

## 再試行・競合・結果不明への対応

| 状態 | 対応 |
| --- | --- |
| 処理中・待機中 | 元の操作IDで `hp_get_operation` を読む。新規操作へ置き換えない。 |
| 転送前の中断 | 保存待ちの同一ZIP・同一操作IDで再開。要約やペイロードを変えない。 |
| 保存済み、ローカル未反映 | 元の受領結果を取得して `accept`。受領対象以後の編集を残す。 |
| 外部処理の結果不明 | 実サービスの読戻しで照合。権限・leaseが有効な場合だけ同じ固定intentを再開。取消し後は読取りに限定する。 |
| 確定した無実行の拒否・古い基準 | 原本と保存待ち情報を保全し、別ディレクトリに最新の作業領域を作り、顧客Codexが必要な変更を移す。不明な旧操作を飛ばして移行しない。 |
| ファイル競合 | B/U/Rの結果を顧客Codexへ返し、内容を確認して解決する。サーバーAIや最終書込み優先で上書きしない。 |
| 公開後の取消し・権限取消し | 外部で完了した事実を保持する。取消しをロールバックと表示しない。キャッシュ整理が未完なら要対応・サイトのブロックを残し、取消し後の追加書込みをしない。 |
| Sheet／メールの問題 | 保存・公開と報告を別に照合し、元の操作の報告処理を復旧する。通知のために新しい公開を作らない。送信API受理と受信箱への到着は区別する。 |
